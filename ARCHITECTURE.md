# Архитектура проекта

Стек: React 19, MobX, TypeScript, Vite, CSS Modules, Biome.

Эталонный пример фичи: [`src/App/SearchBar/`](src/App/SearchBar).

## 1. Фича

Фича — это папка с именем компонента в PascalCase. В корне фичи лежит то, что
описывает её снаружи: разметка, стили, типы и константы. Весь остальной `.ts` —
в папке `logic/`, бизнес-логика — в `logic/tasks/`.

| Файл                                      | Назначение                           |
| ----------------------------------------- | ------------------------------------ |
| `Feature.tsx`                             | View: только разметка                |
| `Feature.module.css`                      | Стили фичи                           |
| `types.ts`, `constants.ts`                | Типы и константы, по необходимости   |
| `logic/usePresenter.ts`                   | Связывает View с логикой             |
| `logic/useXxx.ts`                         | Хуки с отдельными частями презентера |
| `logic/tasks/verb.ts`                     | Таски — бизнес-логика                |
| `logic/xxxStore.ts`, `api.ts`, `utils.ts` | По необходимости                     |

**Любой файл — не больше 120 строк** (для `.ts`/`.tsx` проверяет Biome).
Это страховка, а не причина для разбиения: при правильном разделении логики по
смыслу в лимит не упираешься. Если файл упёрся в 120 строк — в нём смешаны
разные ответственности, их нужно разнести по хукам, таскам или дочерним фичам.

### View — `Feature.tsx`

- Всегда обёрнут в `observer`. Презентер выполняется во время рендера View и
  читает observable-поля; без `observer` компонент не подпишется на их
  изменения и не перерисуется.
- Принимает props и целиком передаёт их в `usePresenter(props)`, сам props не
  читает.
- Из хуков вызывает только `usePresenter` (`./logic/usePresenter`).
- **Можно:** `&&`, тернарники и `.map` по данным презентера; передавать
  значения и обработчики презентера в props детей.
- **Нельзя:** другие хуки, вычисления, обработчики с логикой, сборка
  `className` по условиям — готовый класс возвращает презентер.

### Presenter — `logic/usePresenter.ts`

Презентер связывает React с бизнес-логикой:

- читает сторы и готовит из них данные для View: флаги, списки, `className`;
- держит локальное UI-состояние, рефы и эффекты, разбирает события DOM;
- на действия пользователя вызывает таски. **Сторы меняет только через
  таски**, экшены стора сам не вызывает;
- возвращает объект ровно с тем, что нужно View.

Тип пропсов фичи объявляется и экспортируется здесь, View импортирует его
через `import type`.

Логика презентера делится на хуки **по смыслу**: одна ответственность — один
хук `logic/useXxx.ts` (работа с вводом, обработка клавиатуры, debounce и т.п.).
`usePresenter` собирает их и отдаёт View то, что ему нужно. Эти хуки
импортирует только `usePresenter`, не View.

**Исключение:** если у компонента нет логики (он просто отрисовывает props),
`usePresenter` не нужен — View использует props напрямую, тип пропсов
объявляется в View. Пример:
[`src/App/Results/GenreFilter/GenreChip/`](src/App/Results/GenreFilter/GenreChip).
Свой текст компонент получает из презентера (раздел «Тексты и переводы»),
поэтому без презентера остаются только компоненты, которые отрисовывают
props.

### Таски — `logic/tasks/`

Бизнес существует и внутри, и вне приложения: «найти сериал», «выбрать жанр»,
«выйти из аккаунта» не зависят от того, кнопка это, клавиша или тест.
Бизнес-логика — это варианты использования, каждый вариант — таска.

- Таска — обычная функция, её имя — глагол: `searchShows`, `selectGenre`.
  Одна таска — один файл с её именем.
- Таски не зависят от React: никаких хуков, JSX, событий DOM и рефов. Biome
  запрещает импорт `react`, `react-dom` и `mobx-react-lite` в `logic/tasks/`.
- Со сторами таска общается напрямую: импортирует их и вызывает экшены. Поля
  стора не присваивает. Несколько сторов в одном сценарии связывает таска, а не
  сторы друг друга.
- Запросы к серверу делает через функции из `api.ts`, `fetch` сама не вызывает.
- Может вызывать другие таски.
- Таска, которая может завершиться ошибкой, не бросает исключение, а
  возвращает `{ error: null }` или `{ error }` — что показать пользователю,
  решает вызвавший код. Если ошибку показывает другая ветка дерева, таска
  записывает её в стор.

Пример: [`src/App/logic/tasks/searchShows.ts`](src/App/logic/tasks/searchShows.ts).

### Декомпозиция View

Группа из двух и более значений презентера, которую использует один блок JSX,
становится props дочерней фичи, а блок — этой фичей. Логика презентера, которая
готовит данные только для этого блока, переносится в `usePresenter` дочерней
фичи.

Элемент списка в `.map()` из нескольких элементов разметки оформляй дочерней
фичей.

View родителя после декомпозиции компонует дочерние фичи и выбирает, какую из
них показать.

## 2. Дерево

Структура папок повторяет дерево компонентов. `logic/` и `logic/tasks/` — не
фичи, а часть фичи, в которой лежат.

- **Дочерняя фича**, которая нужна только одному родителю, лежит прямо в папке
  родителя: `InputBox/SmilePicker/`.
- **Переиспользуемый компонент** (нужен двум и более фичам) лежит в папке
  `components/` ближайшего общего предка всех мест использования:
  - `src/components/` — глобальные компоненты;
  - `<Feature>/components/` — компоненты для поддерева этой фичи. Такую папку
    можно создать на любом уровне дерева.
- Компонент в `components/` устроен как обычная фича и подчиняется тем же
  правилам, включая вложенность.
- Если компонент понадобился в другой ветке, он переезжает в `components/`
  ближайшего общего предка.
- **Не-UI модули** (таски, сторы, `api.ts`, `utils.ts`, `types.ts`,
  `constants.ts`) подчиняются тому же правилу **по каждому экспорту**: экспорт
  лежит в ближайшей общей фиче-предке всех мест, где он используется. Внутри
  этой фичи у модуля постоянное место:
  - `types.ts`, `constants.ts` — в корне фичи;
  - сторы, `api.ts`, `utils.ts` — в `logic/`;
  - таски — **всегда** в `logic/tasks/`.

  Константа, нужная только `SearchBar`, лежит в `SearchBar/constants.ts`, а не
  в `App/constants.ts`. Таска, нужная `SearchBar` и `Results`, лежит в
  `App/logic/tasks/`. Глобальные сторы и таски — в `src/logic/` и
  `src/logic/tasks/`.
- Модуль создаётся рядом с первым местом использования и поднимается выше,
  только когда понадобился в другой ветке. Если использования из ветки ушли —
  опускается обратно. Экспорт, который никто не импортирует, не экспортируется.
- Раскладку файлов и размещение экспортов проверяет `npm run check:placement`
  ([`scripts/check-placement.mjs`](scripts/check-placement.mjs)), он входит в
  `npm run check` и `npm run check:fix`.

### Правила импорта

Переиспользование работает **только вниз** по дереву.

| Что                                                                   | Кто может импортировать    |
| --------------------------------------------------------------------- | -------------------------- |
| `logic/usePresenter.ts`, доп. хуки, `*.module.css` фичи               | только файлы этой же фичи  |
| Дочерняя фича `X/Child/`                                              | только View фичи `X`       |
| `X/components/*`                                                      | любой файл в поддереве `X` |
| Таски, сторы, `api.ts`, `utils.ts`, `types.ts`, `constants.ts` из `X` | любой файл в поддереве `X` |

- ✅ `InputBox/SmilePicker` → `src/components/Button`: глобальный компонент.
- ✅ `InputBox/SmilePicker` → `App/components/Avatar`: лежит в `components/`
  предка.
- ✅ `InputBox/SmilePicker` → `App/logic/chatStore`: стор предка.
- ✅ `InputBox/logic/tasks/sendMessage` → `App/logic/tasks/loadHistory`: таска
  предка.
- ❌ `MessageList` → `InputBox/SmilePicker`: чужая ветка. Нужен обоим —
  переносим в `App/components/`.
- ❌ `MessageList` → `InputBox/logic/tasks/sendMessage`: таска чужой ветки.
  Нужна обоим — переносим в `App/logic/tasks/`.
- ❌ `InputBox` → `MessageList`: соседняя фича.
- ❌ `SmilePicker` → `InputBox/logic/usePresenter`: презентер родителя. Данные
  от родителя приходят через props.

### Пути импорта

- Относительно — только своя папка и вглубь: `./logic/usePresenter`,
  `./SmilePicker/SmilePicker`, `./tasks/sendMessage`.
- Всё остальное — через алиас `~/` (это `src/`), в том числе корень своей же
  фичи из `logic/`: `~/App/logic/chatStore`, `~/App/InputBox/constants`,
  `~/components/Button/Button.module.css`.
- `../` не используем — это проверяет Biome (`noRestrictedImports`).
- Алиас объявлен один раз в `paths` из `tsconfig.app.json`, Vite читает его
  оттуда (`resolve.tsconfigPaths`).

## 3. MobX

- **Стор — синглтон модуля.** Файл `chatStore.ts` объявляет класс `ChatStore`
  и экспортирует единственный экземпляр. Класс не экспортируется:

  ```ts
  export const chatStore = new ChatStore();
  ```
- Стор лежит в `logic/` ближайшей общей фичи-предка всех мест использования
  (глобальный — в `src/logic/`). Его импортируют напрямую: ни контекстов, ни
  передачи через props.
- Стор — это состояние, computed и простые экшены (`setPage`, `reset`). Он не
  знает про API, другие сторы и сценарии — их связывают таски.
- Читают стор презентеры и таски, меняют — только таски, через экшены стора.
- В сторах используем `makeAutoObservable(this)`: методы становятся экшенами,
  поэтому таска может вызывать их где угодно, в том числе после `await`.
- Презентер вызывается внутри `observer`-компонента, поэтому чтение
  observable-полей в презентере отслеживается.
- Локальное UI-состояние, которое не нужно таскам (открыт ли список, наведена
  ли карточка), — `useState` в презентере или его хуке.

## 4. Стили

- Только CSS Modules: один `Feature.module.css` на фичу, импортируется как
  `styles`.
- Имена классов — camelCase: `.inputField` → `styles.inputField`.
- Глобальные стили (сброс, CSS-переменные) — только в `src/index.css`.
- Стили фичи не используются другими фичами. Нужен общий вид — делаем
  компонент в `components/`.

## 5. Комментарии

Комментарии не пишем совсем: ни `//`, ни `/* */`, ни JSDoc — в коде, стилях и
конфигах. Если без комментария непонятно — переименуй или разбей код так,
чтобы он читался сам. Отключить правило линтера для файла — через `overrides`
в `biome.json`, а не директивой `biome-ignore`.

## 7. Тексты и переводы

Тексты для пользователя — подписи, `aria-label`, `placeholder`, сообщения об
ошибках — в коде не пишем, только в словарях i18next.

- Словари лежат в `src/locales/<язык>/<namespace>.json`. `translation` —
  тексты интерфейса, ключи сгруппированы по фичам: `searchBar.placeholder`,
  `rentalCard.heading`. `genres` — переводы значений, пришедших из API.
- i18next настраивается один раз в `src/logic/i18n.ts`, его импортирует
  `main.tsx`. Типы ключей объявлены в `src/i18next.d.ts`, поэтому опечатка
  в ключе — ошибка `npm run typecheck`.
- `t` получает только презентер — через `useTranslation()` — и отдаёт View
  готовые строки. View, таски, сторы и `api.ts` переводы не вызывают.
- Сторы и таски хранят данные, не зависящие от языка: исходные значения API
  (`Drama`) и коды (`{ code: "network" }`), а не готовые фразы. Переводит их
  презентер.
- Множественное число — суффиксами i18next (`summary_one`, `summary_few`,
  `summary_many`, `summary_other`) и `t(key, { count })`, без ручного выбора
  формы.
- Не переводятся обозначения, одинаковые на любом языке: `VHS`,
  `PAL · Hi-Fi`, `AV-1`.
- Языки перечислены в `LANGUAGES` (`src/constants.ts`). У каждого языка
  полный набор словарей с теми же ключами, кроме форм множественного числа:
  они свои у каждого языка (`_one`, `_other` в английском; `_one`, `_few`,
  `_many`, `_other` в русском). Типы ключей строятся по русским словарям.
- Текущий язык хранится в URL (`?lang=en`). `src/logic/i18n.ts` читает его
  при старте, а при каждой смене языка записывает обратно в URL, `<html lang>`
  и заголовок вкладки. Язык меняют только через таску `changeLanguage`.
